Accessibility fixes that prove themselves.

verifa11y finds WCAG violations in your HTML, writes the smallest patch for each one and re-checks the page in a real browser. A fix that only silences the checker is thrown out, with the reason.

Get started
$ npx verifa11y audit page.html

Works from the terminal, in Claude Code, Cursor and Codex over MCP, and in GitHub Actions.

verifa11y verify page.html patch.json

The problem

A passing checker is not a fixed page.

Coding agents fix accessibility issues by the hundred, and most confirm the fix by re-running a checker. But “the rule stopped reporting” isn't “the page got better”. Hide the element, add a generic label or restate the file name, and the checker goes quiet.

verifa11y applies every patch to a copy of the page, whoever wrote it (its own codemods, your model or your agent), and keeps it only if it survives checks that a silenced violation doesn't.

How it works

Your file stays put. The patch has to earn its way in.

Every step runs on your machine. A model is only involved if you add one, for the fixes that need judgment.

  1. 01

    Audit

    axe-core runs in headless Chromium. Every violation is mapped to exact lines in your source.

  2. 02

    Patch

    A deterministic codemod when the fix can be proven from the markup; otherwise your model, if configured.

  3. 03

    Shape check

    The patch must quote your file exactly and stay small: at most 6 lines, 2 hunks.

  4. 04

    Apply to a copy

    Same styles and images, page scripts off, other sites blocked. Your file is untouched.

  5. 05

    Verify

    Six checks, below. Any failure rejects the patch and records why.

  6. 06

    Review

    One .patch for git apply, plus a report of what was rejected or skipped.

The verifier

Six checks. None of them trusts the patch.

Each catches a way of making a violation disappear without fixing it, and they apply the same way to every patch, including verifa11y's own.

  • Gone, and nothing new

    axe-core with every WCAG 2.x A and AA rule, on the whole page, not just the rule that was fixed.

    image-alt: gone · 0 new violations

  • Nothing hidden

    No aria-hidden, role="presentation", inert, display:none, clipped text or deleted elements.

    + aria-hidden="true" → rejected

  • Names that mean something

    No “image” or “icon”, no alt text that restates the file name, no label that restates the field's name.

    alt="plot map" = plot-map.png

  • Accessibility tree

    Chromium's computed role, name, states and focusability of every element, before and after the patch.

    img · name "plot map" (was: none)

  • Focus order

    Real Tab presses before and after. An element that leaves the tab order, or a reordered sequence, rejects the patch.

    Tab: 7 stops → 7 stops, same order

  • Pixels and references

    Nothing outside the patch may change on screen, and every aria-controls or aria-labelledby must point at something real.

    aria-controls="false" → no such id

What no automatic check can tell you

verifa11y proves that nothing got worse. It can't prove a fix is what you meant: whether alt text describes what the image is for, whether a state is actually true, whether a colour still fits your design, or the large part of WCAG that isn't machine-testable. Every patch still goes to a person.

Read the naive rows carefully

The naive fixer gets more patches past the verifier than the codemods do, and many are patches a reviewer would reject: invented widget state, inline colour overrides, a live region deleted instead of corrected. None makes the page worse for assistive technology, which is what a verifier can prove.

So “verified” is an upper bound, not a grade. The codemods are at 100% because they decline those cases, not because the verifier would catch them. Every patch and verdict.

Get started

Three ways in. One verifier.

Without a model, verifa11y applies only the fixes it can prove from the markup and tells you why it skipped the rest. Add any model or agent for the fixes that need judgment; its patches go through the same checks.

Node.js 20 or later. Options in the README, instructions for coding agents in AGENTS.md.

Terminal

# once: the browser it renders with
npx verifa11y install-browser

npx verifa11y audit page.html --out findings.json
npx verifa11y fix findings.json --verify --strict
git apply patches/verifa11y.patch

AI agent (MCP)

# Claude Code
claude mcp add verifa11y -- npx -y verifa11y-mcp --root .

# any MCP host (Cursor, Codex, Claude Desktop…)
{ "command": "npx",
  "args": ["-y", "verifa11y-mcp", "--root", "."] }

FAQ

Before you try it.

Does verifa11y make my site accessible?

No. It fixes specific, machine-detectable violations and proves those fixes didn't make anything worse. Most of WCAG can only be judged by a person: whether text alternatives are meaningful, whether the page works with a screen reader, whether the content is understandable. Treat it as a fast, careful first pass, never as a certificate.

Does my code leave my machine?

Not unless you configure a model or agent for the fixes that need judgment; then the page goes to whatever you configured. No telemetry, no account, no server. Pages render offline: requests to any other origin are blocked.

Do I need an AI model?

No. Without one, deterministic codemods fix what can be proven from the markup (misspelled roles, invalid ARIA values, heading levels, simple labels) and everything else is reported as skipped, with the reason. With one (the built-in Claude client, a local model, Claude Code, Codex or any command) it also attempts alt text, colour contrast and widget state.

Which rules does it patch?

image-alt, label, heading-order, aria-allowed-attr, aria-required-attr, aria-valid-attr-value, aria-roles and color-contrast. The verifier checks every WCAG 2.x A and AA rule axe-core has, so a fix for one rule can't quietly break another.

What about React, Vue, Astro or a live site?

Patching works on static HTML files today; templates and frameworks are on the roadmap. verifa11y site crawls and audits a live site with its scripts running, but only reports: a live page has no source file to patch.

How is “verified” different from “passes axe”?

Passing axe means the rule stopped reporting. Verified also means no other violation appeared anywhere on the page, nothing was hidden or deleted, no name became meaningless, and the accessibility tree, focus order and rendered page still agree with the original. On the benchmark, 238 patches pass axe and fail the rest.

Is it free?

Yes: Apache-2.0, on GitHub. Bug reports, rule proposals and contributions are welcome.
